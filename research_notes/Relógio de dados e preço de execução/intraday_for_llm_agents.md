# Intraday (~15-min delayed) prices for LLM agents that reason over daily data: benefits, risks, reproducibility and design

Scope note: the "Cited Findings" sections hold source statements only. Project facts link to this repo's own docs (relative links). Everything computed or recommended by the researcher is under "Inferences". Research date: 2026-10-18.

## 1. Mixing timescales: daily indicators plus a partial current-day bar, as-of construction, and fixed-time snapshots in quant practice

### Takeaway
Charting vendors and backtesting engines treat the still-open daily bar as provisional. Its high, low and close, and every indicator built on them, "repaint" until the session closes. So platforms either deliver only completed bars or push users to the last confirmed bar. Strategies that do act intraday fix a decision clock (for example a signal at 15:45 filled in the closing auction) and use the same snapshot convention in research and in live trading. For this project, that means keeping the 450-day analyst features as of t-1 (confirmed bars only). If intraday information is used at all, it should be one separate, timestamped field, or be used only in deterministic sizing. It should never be a synthetic partial candle pushed into the daily indicators.

### Cited Findings
- TradingView defines repainting as "script behavior causing historical vs realtime calculations or plots to behave differently". On a realtime bar "the high, low and close values are not fixed; they can change values many times before the realtime bar closes"; only the open is fixed. Historical bars store only final OHLC, so realtime results "cannot be repeated on historical bars". — [TradingView, Pine Script docs, "Repainting"](https://www.tradingview.com/pine-script-docs/concepts/repainting/)
- Same doc: adding `barstate.isconfirmed` "requires the script to be executing on the bar's last iteration, when it closes and prices are confirmed". It is "a simple way to avoid repainting" that "will reproduce on historical bars, which are always 'confirmed'", at the cost of later signals. — [TradingView, "Repainting"](https://www.tradingview.com/pine-script-docs/concepts/repainting/)
- Same doc: on historical bars `request.security()` "only returns confirmed values". It "can track unconfirmed values from a higher-timeframe context on realtime bars", for example a daily value on an intraday chart that is still changing, and the script "will repaint them when it restarts its execution". The documented fix is to offset the request by one bar (`[1]`) with `lookahead = barmerge.lookahead_on`, which means using the last completed daily bar. — [TradingView, "Repainting"](https://www.tradingview.com/pine-script-docs/concepts/repainting/)
- QuantConnect/LEAN (forum answers, not official docs): an intraday daily-history request returns the previous day's bar "because the today's close price is available after the market closes and a daily bar is constructed with open/high/low/close". History is indexed by the bar's EndTime, "designed in LEAN to prevent the forward-looking in algorithm trading". Users who want today's values must read the current security price or open explicitly and append it themselves. — [QuantConnect forum #4736](https://www.quantconnect.com/forum/discussion/4736/historical-closing-after-market-opens/); [QuantConnect forum #14362](https://www.quantconnect.com/forum/discussion/14362/history-daily-bars-in-minute-resolution-algo/)
- Fixed-clock snapshot practice. A practitioner study (SPY, proprietary short-term mean-reversion signal) compares three schemes. (1) An idealized signal computed at the close and filled at that same close: about 520% cumulative, 31 bps/trade, 74% hit ratio, 611 trades. (2) "compute signals 15 minutes before the close and execute the trades via Market-on-Close (MOC) orders": about 346%, 27 bps/trade, 71% hit ratio. (3) Close signal with next-open execution: about 254%, 22 bps/trade, 63% hit ratio. About 61% of the 15:45/MOC entries coincide with the idealized entries. The author concludes that "execution delay is a first-order effect rather than a secondary implementation detail" and presents 15:45 to MOC as the practical compromise. The page has no date or sample period, its case labels are inconsistent (figures above follow the body text), and it reports no Sharpe ratios. — [Carlo Zarattini, Concretum Group, "When execution delays erode short-term alpha" (undated, c. Dec 2025)](https://concretumgroup.com/when-execution-delays-erode-short-term-alpha/)
- Practitioner forum: a same-day signal evaluated on close-to-close returns is valid only if the signal is fully known when the position is entered. — [QuantInsti Quantra community thread](https://quantra.quantinsti.com/community/t/backtesting-timing-alignment-signal-shift-vs-return-shift/26696) (forum, secondary)
- As-of (point-in-time) construction in ML practice. Feature stores join each label timestamp to the latest feature row whose timestamp is at or before it, so "future feature values do not leak to models during training". Azure ML defines leakage as "the use of information that isn't expected to be available at prediction time". — [Microsoft Learn, "Offline feature retrieval using a point-in-time join"](https://learn.microsoft.com/en-us/azure/machine-learning/offline-retrieval-point-in-time-join-concepts?view=azureml-api-2); [Feast docs (v0.22 branch)](https://docs.feast.dev/v0.22-branch)
- Caveat on as-of joins: they block future event times but do not by themselves exclude later revisions of a value. The recommended fix is to keep event timestamps separate from created timestamps. — [OneUptime blog, "Keep Feast joins correct with duplicate and late rows" (Aug 2026)](https://oneuptime.com/blog/post/2026-08-15-feast-point-in-time-duplicates-late-rows/view) (third-party, secondary)
- Yahoo Finance lists the São Paulo exchange (BOVESPA, suffix `.SA`) with a 15-min delay, data provider ICE Data Services. — [Yahoo Help, "Exchanges and data providers on Yahoo Finance" (SLN2310)](https://help.yahoo.com/kb/SLN2310.html)
- B3 cash-equity schedule since 9 Mar 2026 (valid until Nov 2026): continuous trading 10:00–16:55 BRT, closing call 16:55–17:00, after-market 17:30–18:00. This is one hour earlier than the previous 17:55 close, a change tied to daylight-saving time abroad. — [Nubank blog](https://blog.nubank.com.br/horario-bolsa-de-valores/); [Money Times](https://www.moneytimes.com.br/b3-b3sa3-muda-horario-de-negociacao-a-partir-de-9-de-marco-veja-o-que-altera-ceci/) (secondary; confirm with B3)
- Project state. DP-26 allows Yahoo intraday bars for the chart only ("não vira marca, preço de operação ou input dos agentes; DP-24 continua com preços de referência"). Yahoo deletes 1-min bars after ~30 days (5-min after 60, 1-h after 730), and the open session is held in memory with ~15-min delay. DP-27: "as-of" queries see only sessions up to the decision date. — [DIRECAO_DO_PROJETO.md, DP-26/DP-27](../../docs/DIRECAO_DO_PROJETO.md)
- Project data audit: the Yahoo intraday timestamps (`regularMarketTime`) "não foram validados como horário de publicação". — [AVALIACAO_COLETA_DADOS_2026-10-14.md](../../docs/AVALIACAO_COLETA_DADOS_2026-10-14.md)

### Inferences
- Indicators computed on a partial bar are a different random variable from the same indicator on complete bars. RSI, MA, Bollinger %B or ATR computed with a 13:00 "close" do not have the distribution of the 449 complete bars behind them. Volume-based features (today's volume against a 450-day history) are mechanically biased downward intraday, and range-based features (high-low, ATR) are biased low early in the session. Appending a partial bar to the 450-day window therefore creates history/live skew: the LLM gets a value that has no counterpart in its own history.
- A clean as-of design keeps two separate clocks. The data clock is the last complete B3 session (t-1) for every 450-day feature, as today. The price clock is a declared snapshot record: value, quote time, fetch time, source, declared delay, and session state. They should be two labeled objects in the sealed context. The snapshot should never be written into the daily series.
- The human triggers runs at arbitrary times, so an intraday field means different things at 10:05 and at 16:40. If one is given to an LLM it must carry the quote timestamp and the fraction of the session elapsed. Otherwise "+0.8% today" looks the same at both times.
- A fixed-clock policy (for example "snapshot at 16:00 BRT") cannot be backtested over long periods with the project's sources. Yahoo keeps 1-h bars for only ~2 years (DP-26), and COTAHIST is daily. Snapshots must be stored when the decision is made, because they cannot be rebuilt afterwards.
- The Brazilian analog of Concretum's "15:45 to MOC" is a decision before the 16:55 closing call that uses a ~15-min delayed quote for sizing, with the fill recorded at the official closing-call price (or the next opening auction, which matches the protocol's earlier `OPENING_AUCTION_EXECUTION`). The fill is then official, reproducible from COTAHIST, and strictly after the decision. The delayed quote only affects quantities.

### Gaps
- No primary Quantopian/Zipline documentation was retrieved (the platform is shut down). LEAN behavior comes from forum answers, not official docs.
- No academic study was found that measures the error of computing daily technical indicators on partial bars.
- B3 closing-call order-entry rules (cut-off times, imbalance publication) were not checked against a B3 primary source. The schedule above comes from secondary sites.
- Not verified whether Yahoo's `.SA` delay is always exactly 15 min, or whether its timestamps are trade time or publication time (the project's own audit also leaves this open).

## 2. LLM numeracy, sensitivity to small numeric/prompt changes, run-to-run variance, and what a moving input does to reproducibility and A/B comparison

### Takeaway
Evidence from 2023–2026 shows that LLM outputs move with changes to numbers and formatting that should be irrelevant, that models anchor on numbers in the prompt, and that hosted inference is not reproducible even at temperature 0. This project samples at temperature 1.0. Trading agents in particular show large run-to-run variance and action flipping. A moving price adds a second variance source, input drift tied to trigger time, on top of sampling noise. Without paired runs and replicates, a difference between runs with and without intraday data cannot be interpreted.

### Cited Findings
- GSM-Symbolic: the "performance of all models declines when only the numerical values in the question are altered". Adding one seemingly relevant but irrelevant clause (GSM-NoOp) caused drops of up to 65% across state-of-the-art models. — [Mirzadeh et al. (Apple), 2024, "GSM-Symbolic: Understanding the Limitations of Mathematical Reasoning in Large Language Models", arXiv:2410.05229](https://arxiv.org/abs/2410.05229). A 2026 re-examination questions whether frontier models still fail ([LessWrong, "Revisiting GSM-Symbolic"](https://www.lesswrong.com/posts/Ze4C99Dasj74YKCFh/revisiting-gsm-symbolic-models-seem-to-reason-okay-actually)); its results were not verified.
- Number Cookbook: LLMs that handle complex reasoning still fail basic number understanding and processing, for example judging 9.11 larger than 9.9. On 17 tasks across 4 number representations (41 combinations), "current LLMs fail frequently in many of the tasks". Chain-of-thought and existing fixes "have their own drawbacks". — [Yang, Hu, Kang, Lin, Zhang, ICLR 2025, "Number Cookbook: Number Understanding of Language Models and How to Improve It", arXiv:2411.03766](https://arxiv.org/abs/2411.03766v1)
- Formatting sensitivity: performance differences of "up to 76 accuracy points" from formatting changes alone (LLaMA-2-13B). The sensitivity persists with larger models, more few-shot examples and instruction tuning, and format effects correlate only weakly across models. The authors recommend reporting a range across plausible formats. — [Sclar, Choi, Tsvetkov, Suhr, ICLR 2024, "Quantifying Language Models' Sensitivity to Spurious Features in Prompt Design...", arXiv:2310.11324](https://arxiv.org/abs/2310.11324v1)
- Anchoring on prompt numbers: anchoring is common in widely used LLMs, appears in shallow layers, and is not removed by conventional mitigations, though reasoning helps somewhat. — [Huang et al., 2025, SynAnchors study, arXiv:2505.15392](https://arxiv.org/pdf/2505.15392v1.pdf) (title not verified). Susceptibility tracks model confidence more than accuracy, and high anchors move models more than low anchors. — [Owusu & Feldman, ACL 2026 (short), "Anchoring Depends on Confidence and Post-Training in Language Models"](https://aclanthology.org/2026.acl-short.16/). Simple prompt-level mitigations were "largely ineffective" for GPT-3.5/4/4o (Lou & Sun 2024, as summarized in [arXiv:2511.05766, "Anchors in the Machine"](https://arxiv.org/pdf/2511.05766)).
- LLMs and raw numeric series: removing the LLM from popular LLM-based time-series forecasters, or replacing it with a basic attention layer, "does not degrade" and often improves forecasting. Pretrained LLMs "do not represent the sequential dependencies in time series" and cost orders of magnitude more compute. — [Tan, Merrill, Gupta, Althoff, Hartvigsen, NeurIPS 2024, "Are Language Models Actually Useful for Time Series Forecasting?", arXiv:2406.16964](https://arxiv.org/abs/2406.16964v2)
- Non-determinism at "deterministic" settings: five LLMs, eight tasks, 10 runs. Accuracy varied by up to 15% across runs, and the gap between best and worst achievable performance reached up to 70%. "None of the LLMs consistently delivers repeatable accuracy across all tasks, much less identical output strings." The authors propose agreement metrics TARr@N (raw output) and TARa@N (parsed answer). — [Atil et al., 2024/2025, "Non-Determinism of 'Deterministic' LLM Settings", arXiv:2408.04667](https://arxiv.org/abs/2408.04667)
- Cause of hosted-endpoint non-determinism: load-dependent batch size, so kernels are not batch-invariant ("the primary reason nearly all LLM inference endpoints are nondeterministic"). In 1,000 temperature-0 completions of one prompt (Qwen3-235B), there were 80 unique completions, identical for the first 102 tokens. With batch-invariant kernels all 1,000 were identical, at roughly 1.6–2.1x runtime in their test. "LLM APIs are still not deterministic in practice." — [Horace He, Thinking Machines Lab, "Defeating Nondeterminism in LLM Inference", 10 Sep 2025](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- Provider parameter docs (Anthropic wording, as reproduced by a third-party SDK): "even with temperature of 0.0, the results will not be fully deterministic". — [CAMEL-AI docs, Anthropic config](https://docs.camel-ai.org/reference/camel.configs.anthropic_config) (secondary; the project's model is Gemini, whose determinism was not checked)
- Finance/accounting consistency: 50 independent runs on identical inputs across five tasks with GPT-3.5-turbo, GPT-4o-mini and GPT-4o. The authors find "substantial but task-dependent consistency", with "binary classification and sentiment analysis achieving near-perfect reproducibility" and more variability on complex tasks. "simple aggregation strategies across 3-5 runs dramatically improve consistency", and "downstream statistical inferences remain remarkably robust". — [Wang & Wang, 2025 (v4 13 Sep 2025), "Assessing Consistency and Reproducibility in the Outputs of Large Language Models: Evidence Across Diverse Finance and Accounting Tasks", arXiv:2503.16974](https://arxiv.org/abs/2503.16974)
- Trading agents specifically: LLM trading agents "exhibit extreme run-to-run variance", "generate inconsistent action sequences even under deterministic decoding", and "frequently produce irrational action flipping across adjacent time steps". The authors attribute this to the "stateless autoregressive nature of LLMs" and "sensitivity to continuous-to-discrete action mappings in portfolio allocation tasks". — [Zhang et al., 2026, "AlphaForgeBench: Benchmarking End-to-End Trading Strategy Design with Large Language Models", arXiv:2602.18481](https://arxiv.org/abs/2602.18481)
- Project evidence: the two Global PM runs (V1, V2) used temperature 1.0 with n=1 per treatment. The project's own note: "A tabela descreve o que foi observado; não estima efeito de tratamento". The frozen context is identified by a SHA-256 hash. — [COMPARISON_V1_V2.md](../../docs/evidence/hfl_scientific_consolidation_v75/COMPARISON_V1_V2.md)

### Inferences
- At temperature 1.0 every run is already a random draw. With a moving price the prompt also becomes a function of trigger time, and the two variance sources are confounded. The achievable form of reproducibility then becomes:
  - (a) a byte-exact, sealed prompt, so anyone can see exactly what the model saw;
  - (b) distributional reproducibility, measured with replicates.

  Identical outputs are not achievable. Sealing the snapshot inside the hashed context preserves auditability even though outputs cannot be reproduced bit for bit.
- A 15-min delayed quote differs from the "true" price by roughly 0.3–0.4% (1 sigma; see Section 4). That is the size of change the GSM-Symbolic, anchoring and formatting results suggest can flip outputs for spurious reasons. A decision flip after such a change cannot be told apart from sampling noise without replicates. AlphaForgeBench's "action flipping" result suggests that adding a number that changes from run to run should increase flip rates.
- Human-triggered timing is an uncontrolled covariate. If runs tend to be triggered after visible price moves, the "with intraday" condition is selected on market state. Any comparison must therefore pair both arms on the same snapshot, at the same moment, with the same model version.
- Numeracy and anchoring argue against raw absolute prices in prompts. If intraday information is given, it should be a precomputed relative quantity, for example "return since previous close as of 14:20, 60% of session elapsed: -0.6%", not "37.18 vs 37.42". This keeps arithmetic in code (see Section 3).
- Anonymization risk: an exact absolute price, together with features and a decision-date context, is a fingerprint that could help a model recall a specific ticker and date from memorized price history. That would weaken the project's no-ticker/no-date design. Relative, rounded values carry less of that risk. This builds on the distraction and memorization findings in Section 6.
- Aggregating 3–5 replicates (Wang & Wang) would reduce noise but multiplies paid calls. Under the project's budget cap this is probably not affordable for analysts (see Section 5).

### Gaps
- No study was found that measures how often LLM trading decisions flip under small (<1%) price perturbations with everything else held fixed. This is the quantity most relevant here and it is untested.
- The determinism and seed behavior of the project's model (gemini-3.8-flash) was not checked.
- Two numbers seen only in search snippets were not verified and are not used: Backtrader-Bench ("76.7% single run vs 64.3% mean of 10 runs", arXiv:2608.11232), and an intraclass correlation of 0.63 to 0.89 attributed to Business Arena (arXiv:2608.08621), which does not appear in that paper's abstract.

## 3. Separation of concerns: "LLM decides direction/target weights, deterministic code sizes quantities at execution price" vs "LLM sizes quantities directly"

### Takeaway
Mainstream quant frameworks and most published LLM-finance systems keep the model at the level of direction, insight or weights, and let deterministic code turn that into quantities at the execution-time price. Examples: QuantConnect (Insight to PortfolioTarget to Execution), FinCon (LLM decides per-asset trades, a mean-variance solver sets the weights), LiveTradeBench (LLM outputs an allocation vector, the environment converts it at the next price) and AlphaForgeBench (LLM writes strategies, execution is deterministic, which "decouples reasoning from execution mechanics"). This project had exactly that split (PortfolioAction with no size field) before DP-24 moved to LLM-proposed quantities at displayed reference prices. With the split, the current price can improve sizing without entering any prompt.

### Cited Findings
- QuantConnect Algorithm Framework. Pipeline: Universe Selection, Alpha (signals as Insight objects), Portfolio Construction, Risk Management, Execution. "Insight objects from the Alpha model are fed into the Portfolio Construction model to create PortfolioTarget objects", each giving the units to hold. The Execution model receives risk-adjusted targets and works to reach them (for example `ImmediateExecutionModel` sends market orders). The docs say the framework suits rebalancing, ranking and multi-factor strategies best. — [QuantConnect docs, Algorithm Framework overview](https://www.quantconnect.com/docs/v2/writing-algorithms/algorithm-framework/overview); [Portfolio Construction (v1)](https://www.quantconnect.com/docs/v1/algorithm-framework/portfolio-construction); [Execution (v1)](https://quantconnect.com/docs/v1/algorithm-framework/execution)
- FinCon (NeurIPS 2024): in portfolio tasks the manager agent "makes trading decisions for each stock in the pool", and weights come from an external "optimization solver that applies the mean-variance optimization". — [Yu et al., 2024, "FinCon: A Synthesized LLM Multi-Agent System with Conceptual Verbal Reinforcement for Enhanced Financial Decision Making", arXiv:2407.06567](https://arxiv.org/pdf/2407.06567v3); [author PDF](https://suchow.io/assets/docs/yu2024fincon.pdf)
- TradingAgents generates "trading signals to buy, sell, or hold assets, which are then executed". The trader role description includes "Deciding on the timing and size of trades", but the sizing mechanism is not described. Agents receive "Sixty standard technical analysis indicators" and news, and "make decisions based solely on data available up to each trading day". — [Xiao, Sun, Luo, Wang, 2024, "TradingAgents: Multi-Agents LLM Financial Trading Framework", arXiv:2412.20138](https://arxiv.org/html/2412.20138v4)
- LiveTradeBench: the agent "outputs percentage allocations", a target allocation vector summing to 1. Holdings are rebalanced as q_{t+1} = v_{t+1} · a_t / p_{t+1}, "without modeling low-level order execution mechanics". — [Yu, Li, You (UIUC), Nov 2025, "LiveTradeBench: Seeking Real-World Alpha with Large Language Models", arXiv:2511.03628](https://arxiv.org/html/2511.03628v1)
- AlphaForgeBench treats LLMs as quantitative researchers that "generate executable alpha factors and compose factor-based trading strategies". This enables "deterministic and reproducible evaluation", "decouples reasoning from execution mechanics", and is reported to eliminate execution-induced instability. — [Zhang et al., 2026, arXiv:2602.18481](https://arxiv.org/abs/2602.18481)
- Offloading arithmetic: in PAL the LLM writes a program and a Python interpreter does the computation. This was more accurate than much larger models doing chain-of-thought arithmetic: +15 points top-1 over PaLM chain-of-thought on GSM8K. — [Gao, Madaan, et al., ICML 2023, "PAL: Program-aided Language Models", arXiv:2211.10435](https://arxiv.org/abs/2211.10435v1)
- Robo-advisor practice (Betterment's own disclosures). Rebalancing is rule-based against a target allocation: cash flows are used first, then overweight holdings are sold and underweight ones bought when drift exceeds a tolerance. Disclosures give the default threshold as 3% (5% in a later page for mutual-fund portfolios), and the thresholds may change. — [Betterment, "Rebalancing methods"](https://www.betterment.com/help/portfolio-rebalancing-methods); [Betterment, "Rebalancing and Auto-Adjust Disclosure"](https://www.betterment.com/legal/auto-adjust-disclosure) (thresholds conflict across pages)
- Project history: the earlier protocol used deterministic sizing (approved BUY to `target_weight = long_target_weight`, SELL to 0). "O gestor de portfólio não tem autoridade para escolher a quantidade financeira: o schema `PortfolioAction` não possui campo de tamanho". — [EXPERIMENT_PROTOCOL.md](../../docs/EXPERIMENT_PROTOCOL.md)
- Project today (DP-24): the PM proposes coordinated quantities, partial or total. "Lucas escolheu registrar a simulação aos preços de referência exibidos, enquanto cotação do momento não está integrada", and the rule is not to "apresentar fechamento anterior como preço ao vivo". The 15/10 change log notes Lucas's "desejo futuro de cotação do momento". — [DIRECAO_DO_PROJETO.md, DP-24](../../docs/DIRECAO_DO_PROJETO.md). The PM receives a frozen RAW B3 CLOSE. The backend derives positions, weights and cash, and rejects uncovered sells, credit, incomplete baskets, fractional shares, and operations that contradict an opinion or veto. — [ESTADO_ATUAL.md](../../docs/ESTADO_ATUAL.md)

### Inferences
- Robustness to price drift:
  - If the LLM outputs target weights or target values per asset, its intent does not depend on price. Quantities are recomputed at whatever execution reference is chosen, so a stale view affects what to hold, not the arithmetic.
  - If the LLM outputs share counts at P_ref, a move dP shifts realized value by about q·P_ref·(dP/P_ref). A buy plan that uses nearly all cash can turn into negative cash at the execution price, and the backend's no-credit rule would then reject it. A plan validated at the previous close is therefore not guaranteed to be feasible later.
- An option compatible with DP-24 (needs Lucas's decision, because it changes DP-24's semantics):
  1. The PM keeps proposing quantities at the displayed reference price.
  2. The system stores them as intended value (q × P_ref) per asset.
  3. A deterministic step re-sizes to whole shares at the execution reference (delayed snapshot or official auction price), with an explicit cash and cost buffer, and the existing veto/opinion/no-credit validation.
  4. The UI shows both the LLM's proposal and the re-sized order.

  The LLM never sees the live price, and the sizing benefit is captured in code.
- Under this split, the evaluation of "does a current price help?" for sizing is deterministic and costs nothing: replay stored snapshots against the official fill (Section 5). It needs no paid A/B.
- Asking the LLM to compute quantities from a price is the kind of arithmetic that PAL and Number Cookbook show is error-prone. The existing backend validators are a guard, but a guard can only reject a bad plan. A deterministic sizer produces a correct one.

### Gaps
- The open-source virattt/ai-hedge-fund portfolio manager (which, from memory, computes maximum shares from price and risk limits before the LLM chooses) could not be verified: both file URLs returned 404 and the README no longer lists the agents. It is omitted as evidence.
- No head-to-head study was found comparing "LLM sizes quantities" with "LLM sets weights plus deterministic sizing" under identical conditions. AlphaForgeBench is the closest, with a different task framing.
- Robo-advisor evidence is limited to Betterment's own disclosures, which conflict on thresholds.

## 4. Latency: multi-agent pipeline runtime vs intraday movement; risk of stale prompts

### Takeaway
LLM runtime is not the binding latency. The project's PM calls took about 17–20 s, and published multi-agent systems use around 11 LLM calls plus 20+ tool calls per decision, which is minutes at most. Both are small next to the ~15-min quote delay. All of these are dwarfed by the gap between the reference price used today (the previous session's close) and the moment of human approval or execution, which can be hours under a 24-h proposal validity. Staleness is driven by the human-in-the-loop and by the reference-price convention.

### Cited Findings
- Project: the two real Global PM calls lasted 16.9 s and 19.5 s (n=1 each; gemini-3.8-flash, `thinking_level` low, temperature 1.0, one HTTP attempt). Proposal validity is 24 h (for example "até 13/10 15:18 BRT no V1"). — [COMPARISON_V1_V2.md](../../docs/evidence/hfl_scientific_consolidation_v75/COMPARISON_V1_V2.md). The runbook lists the global preflight with "validade 24 h". — [HFL_OPERATIONS_RUNBOOK.md](../../docs/HFL_OPERATIONS_RUNBOOK.md)
- TradingAgents ran its backtest over only 3 months "due to intensive LLM and tool use (11 LLM calls & 20+ tool calls/prediction)", and reports no wall-clock or per-day cost figures. — [Xiao et al., arXiv:2412.20138](https://arxiv.org/html/2412.20138v4)
- LiveTradeBench (live, 50 trading days) uses "closing prices" as observations and does not state a fixed decision time, snapshot, or latency figures. — [Yu, Li, You, arXiv:2511.03628](https://arxiv.org/html/2511.03628v1)
- Quote delay for `.SA` on Yahoo: 15 min. — [Yahoo Help SLN2310](https://help.yahoo.com/kb/SLN2310.html). Session 10:00–16:55 BRT with closing call 16:55–17:00 (current schedule). — [Nubank blog](https://blog.nubank.com.br/horario-bolsa-de-valores/) (secondary)
- Project: the PM receives the "CLOSE RAW B3 congelado". — [ESTADO_ATUAL.md](../../docs/ESTADO_ATUAL.md). The simulated portfolios start with R$ 100 mil each. — [DIRECAO_DO_PROJETO.md, DP-20](../../docs/DIRECAO_DO_PROJETO.md)
- Execution delay has first-order effects on short-horizon signals (15:45 to MOC vs next open). — [Zarattini, Concretum](https://concretumgroup.com/when-execution-delays-erode-short-term-alpha/)

### Inferences
- Illustrative volatility arithmetic. Assumptions: annualized volatility 30% (sigma_daily = 0.30/sqrt(252) ≈ 1.89%), a 415-min session, variance spread evenly over trading time, overnight gaps ignored. Real intraday volatility is usually higher near the open and close, so these figures understate moves at those times. One-sigma price move over each interval (expected absolute move ≈ 0.8 × sigma):

  | Interval | 1-sigma move |
  |---|---|
  | One 20-s LLM call | ≈ 0.05% |
  | A 2-min pipeline | ≈ 0.13% |
  | The 15-min quote delay | ≈ 0.36% |
  | Delay plus pipeline (17 min) | ≈ 0.38% |
  | A 1-h human approval lag | ≈ 0.72% |
  | Previous close to end of today's session | ≈ 1.89% (plus the overnight gap) |

  The ranking holds for any volatility level: previous-close reference >> human lag > quote delay >> LLM runtime.
- Sizing impact for a R$20k position (20% of R$100k): the 1-sigma value error is about R$72 with a 15-min delayed quote, against about R$378 with the previous close. Whole-share rounding already leaves a residual of up to one share price per asset, the same order as the delayed-quote error. A ~15-min delayed quote therefore captures most of the achievable sizing accuracy, and a real-time feed would add little next to rounding and costs.
- Stale prompts: a prompt built at t0 and approved at t1 should carry a declared staleness budget.
  - If more than X minutes have passed, or the price has moved more than Y% since t0, re-snapshot and re-size deterministically (no new LLM call).
  - Re-run the LLM only past a larger, pre-declared move threshold that could plausibly change the thesis.

  This is the time-of-check versus time-of-use problem: validation at t0 does not guarantee feasibility at t1, so validation must be repeated at use time.
- The LLM's view is anchored at t-1 regardless (450-day features up to the previous session). Giving the LLM a 15-min delayed price narrows the information gap only a little relative to its whole horizon. The sizing gap closes much more when that price goes into the deterministic sizer.

### Gaps
- No literature was found reporting end-to-end wall-clock times for multi-agent LLM trading pipelines. Papers report call counts, not latency.
- No B3-specific intraday volatility profile was sourced, so the uniform-variance assumption is unvalidated for these five stocks.
- The project's analyst-call latency, and whether analysts run in parallel, were not checked. Only the two PM calls have recorded durations.

## 5. How to evaluate whether intraday information helps: paired/shadow designs, pre-registration, sample size, defensible thesis claims

### Takeaway
With daily decisions on five correlated assets, evidence from P&L or Sharpe that intraday information helps is out of reach in a thesis timeframe: it needs years even with paired arms. Three kinds of claim are defensible:
1. Process and auditability claims.
2. Decision-level paired comparisons against a measured noise floor (disagreement between arms vs within arms).
3. Deterministic measurements of sizing error and feasibility, replayed from stored snapshots.

All of these should be pre-registered, reported in neutral language (DP-09) and run only prospectively (DP-31). Prompt-level A/B tests are also budget-bound: about 31 PM calls in total under the current cap.

### Cited Findings
- "Evaluations are experiments". Miller gives formulas for analyzing eval data, measuring differences between two models, and planning experiments. For paired designs the standard error is computed from per-question differences, and paired variance equals unpaired variance minus a covariance term, so positively correlated arms give tighter intervals. — [Evan Miller (Anthropic), 2024, "Adding Error Bars to Evals: A Statistical Approach to Language Model Evaluations", arXiv:2411.00640](https://arxiv.org/pdf/2411.00640)
- Aggregating 3–5 runs "dramatically" improves consistency, and downstream inference stays robust. — [Wang & Wang, arXiv:2503.16974](https://arxiv.org/abs/2503.16974). Agreement-rate metrics across N runs (TARr@N, TARa@N). — [Atil et al., arXiv:2408.04667](https://arxiv.org/abs/2408.04667)
- Report a range across plausible prompt formats rather than one format. — [Sclar et al., arXiv:2310.11324](https://arxiv.org/abs/2310.11324v1)
- Minimum Track Record Length (MinTRL): the track-record length needed to reject, at a given confidence, that the true Sharpe ratio is below a threshold. Negative skew and fat tails lengthen it. — [Bailey & López de Prado, 2012, "The Sharpe Ratio Efficient Frontier", Journal of Risk](https://www.risk.net/journal-risk/2223785/sharpe-ratio-efficient-frontier). The Deflated Sharpe Ratio corrects for "Selection bias under multiple testing and non-Normally distributed returns". — [Bailey & López de Prado, 2014, SSRN 2460551](https://papers.ssrn.com/abstract=2460551)
- "With the combination of unreported tests, lack of adjustment for multiple tests, and direct and indirect p-hacking, many of the results being published will fail to hold up in the future." — [Harvey, 2017, "Presidential Address: The Scientific Outlook in Financial Economics", Journal of Finance](https://people.duke.edu/~charvey/Research/Published_Papers/P131_The_scientific_outlook.pdf)
- Pre-registration alone showed "no meaningful difference" in test-statistic distributions, but "pre-registered studies that have a complete PAP [pre-analysis plan] are significantly less p-hacked" (15,992 test statistics from RCTs in 15 economics journals). — [Brodeur, Cook, et al., "Do Pre-Registration and Pre-Analysis Plans Reduce p-Hacking and Publication Bias?" (JPE Microeconomics, 2024)](https://siepr.stanford.edu/publications/working-paper/do-pre-registration-and-pre-analysis-plans-reduce-p-hacking-and)
- A lightweight pre-registration template for predictive modeling, plus a discussion of what pre-registration can and cannot fix in ML. — [Hofman, Chatzimparmpas, Sharma, Watts, Hullman, 2023, "Pre-registration for Predictive Modeling", arXiv:2311.18807](https://arxiv.org/abs/2311.18807v1)
- Over 2000–2024 and 100+ symbols, "previously reported LLM advantages deteriorate significantly under broader cross-section and over a longer-term evaluation". LLM strategies were too conservative in bull markets and too aggressive in bear markets. — [Li, Kim, Cucuringu, Ma, 2025, "Can LLM-based Financial Investing Strategies Outperform the Market in Long Run?" (FINSABER), arXiv:2505.07078](https://arxiv.org/abs/2505.07078)
- A live 50-day evaluation of 21 LLMs found that high LMArena scores do not imply better trading outcomes. — [LiveTradeBench, arXiv:2511.03628](https://arxiv.org/html/2511.03628v1)
- Many existing trading benchmarks are hard to reproduce because of run-to-run variance; deterministic execution of LLM-written strategies fixes this. — [AlphaForgeBench, arXiv:2602.18481](https://arxiv.org/abs/2602.18481)
- Project budget: "cada chamada do gestor reserva cerca de US$ 0,16 contra o teto acumulado de US$ 5 ... Isso dá cerca de 31 chamadas ao todo, antes de qualquer A/B". — [PESQUISA_MUNICAO_AGENTES.md](../../docs/PESQUISA_MUNICAO_AGENTES.md). The observed monetary floor per PM call was US$0.0235–0.0263 (billing unconfirmed). — [COMPARISON_V1_V2.md](../../docs/evidence/hfl_scientific_consolidation_v75/COMPARISON_V1_V2.md)
- Project decisions: DP-31, AI agents evaluated only prospectively, because past backtests are "caro e contaminado". DP-28 requires neutral language, noting that an observed difference does not demonstrate superiority (DP-09). — [DIRECAO_DO_PROJETO.md](../../docs/DIRECAO_DO_PROJETO.md)

### Inferences
- Sample-size reality (standard normal-approximation formulas, computed here):
  - Directional hit rate of 55% vs 50% (alpha 0.05 two-sided, power 0.8): about 783 independent decisions. That is about 157 sessions with 5 assets/day if the decisions were independent. With a same-day cross-asset correlation of 0.3 (design effect 1 + 4 × 0.3 = 2.2) it is about 345 sessions, roughly 1.4 years of B3 sessions.
  - A Sharpe difference of 0.5 between two paired arms: Var(SR_A − SR_B) ≈ 2(1−rho)/T years for small Sharpe and iid returns, so T ≈ (z_alpha + z_beta)² · 2(1−rho) / 0.25. With rho = 0.9 that is about 6.3 years at 80% power (about 3.1 years at 50%). With rho = 0.5 it is about 31 years.

  Conclusion: P&L-based claims about intraday information are not defensible within a TCC.
- Recommended design for any LLM-prompt test:
  1. **Pre-register** in the repo (dated and hashed): hypothesis, arms, snapshot policy, primary endpoint, analysis, stopping rule, and what counts as "no effect". Use a complete analysis plan, since Brodeur et al. find pre-registration without a PAP ineffective.
  2. **Pair each session.** Build both arms from the same sealed context, identical except for the intraday field, and run them at the same time with the same model. Run in consultative or shadow mode: only the control policy, or neither arm, touches the ledger.
  3. **Measure the noise floor.** Run k ≥ 2 (ideally 3) replicates per arm. Estimate within-arm agreement (TARa@k) and between-arm disagreement. The effect is between-arm disagreement minus within-arm disagreement, with standard errors clustered by session.
  4. **Endpoints.** Primary: decision flip rate, and the direction of flips relative to the intraday move (does the treatment arm chase same-day moves? This is a momentum and anchoring diagnostic). Also validator rejection rate. Secondary, descriptive only: next-session outcomes of flipped decisions.
  5. **Deterministic sizing, evaluated separately and at zero inference cost.** Compare |realized weight − target weight|, plan feasibility (cash ≥ 0), and residual cash under P_ref ∈ {previous close, delayed snapshot} against the official fill. This is fully replayable.
- Cost per session = arms × replicates × calls per run × price per call. For example 2 × 3 × 6 (5 analysts + 1 PM) = 36 calls. That is about US$5.76 at the US$0.16 reserve, more than the entire US$5 cap in one session, or about US$0.9 at the observed ~US$0.025 floor. A prompt-level A/B therefore needs an explicit budget decision from Lucas. Using the price for sizing only does not.
- Claims a thesis can defend:
  - Defensible: "Under pre-registered protocol X, adding the intraday field changed N% of decisions against a within-arm noise floor of M% (CI ...)".
  - Defensible: "Deterministic sizing at a ~15-min delayed quote reduced sizing error and infeasible plans from A to B over S sessions".
  - Defensible: "Every input, including the snapshot, is sealed and replayable".
  - Not defensible with this sample: "intraday information improved returns or Sharpe".

### Gaps
- Lo (2002), "The Statistics of Sharpe Ratios", and the Jobson–Korkie/Memmel or Ledoit–Wolf (2008) tests for Sharpe differences were not retrieved. The Sharpe-difference approximation above is standard but was not re-verified in this session.
- No empirical estimate of within-arm decision agreement exists yet for the project's model and prompts at temperature 1.0. It must be measured.
- It was not verified whether Harvey (2017) explicitly endorses pre-registration; the cited sentence is about p-hacking.
- Miller's full list of recommendations was not read in full text. The paired-difference description comes from the paper's PDF as surfaced by search.

## 6. Guidance on point-in-time data, data snapshots, sealing inputs and temporal leakage (AI/LLM evaluation literature)

### Takeaway
LLM-finance evaluation work from 2023–2026 converges on four practices:
1. Prospective/live evaluation or point-in-time models, because pretrained LLMs memorize outcomes (look-ahead) and are distracted by what they know about named entities.
2. Anonymized entities.
3. Inputs that are strictly as-of the decision time and can be replayed.
4. Fixed, recorded model versions.

For intraday prices this means: snapshot at decision time, seal the snapshot with its timestamps and hash inside the context, never rebuild it later, and keep it out of the anonymized analyst inputs, or include it only as a coarse relative quantity.

### Cited Findings
- Two biases from pretrained LLMs in backtests: "a look-ahead bias, in which the LLM may have specific knowledge of the stock returns that followed a news article, and a distraction effect, in which general knowledge of the companies named interferes with the measurement of a text's sentiment". In-sample, anonymized headlines performed better, more so for large firms. The authors find anonymization useful out of sample too. — [Glasserman & Lin, 2023, "Assessing Look-Ahead Bias in Stock Return Predictions Generated By GPT Sentiment Analysis", arXiv:2309.17322 (J. Financial Data Science, 2024)](https://arxiv.org/abs/2309.17322)
- Point-in-time LLMs: a series of models each trained only on data before a cutoff, designed to be "nonprognosticative" and to avoid both future facts and future language change. — [Drinkall, Rahimikia, Pierrehumbert, Zohren, Findings of NAACL 2024, "Time Machine GPT", arXiv:2404.18543](https://arxiv.org/abs/2404.18543v1)
- Chronologically consistent models trained only on text available at each point in time. In next-day return prediction from news, the v3 abstract says lookahead bias appears modest. — [He, Lv, Manela, Wu, 2025, "Chronologically Consistent Large Language Models", arXiv:2502.21206](https://alphaxiv.org/abs/2502.21206). A follow-up describes instruction-following versions with fully open, fixed weights that "guarantee replicability". — [He et al., Oct 2025, "Chronologically Consistent Generative AI", arXiv:2510.11677](https://arxiv.org/abs/2510.11677v1)
- Many LLM trading agents' backtest profits vanish once the test period falls after the model's knowledge cutoff, which the authors attribute to memorization. They propose a leakage benchmark (FinLake-Bench) and counterfactual-perturbation training (FactFin). — [Li et al., Oct 2025, "Profit Mirage: Revisiting Information Leakage in LLM-based Financial Agents", arXiv:2510.07920](https://arxiv.org/abs/2510.07920v1). Specific figures in secondary summaries (more than 85% accuracy on "did the market rise on date T?" probes; a 50% drop for the best agent) were not verified in the full text.
- "Results reveal significant lookahead bias in standard LLMs, as measured with alpha decay" across temporally distinct regimes. Point-in-time models (Pitinf) show less of it. — [Benhenda, Jan 2026, "Look-Ahead-Bench: a Standardized Benchmark of Look-ahead Bias in Point-in-Time LLMs for Finance", arXiv:2601.13770](https://arxiv.org/abs/2601.13770)
- Live streaming evaluation removes "the dependence on offline backtesting", avoiding "information leakage from the root". — [LiveTradeBench, arXiv:2511.03628](https://arxiv.org/html/2511.03628v1)
- A backtest framework designed to address survivorship, look-ahead and data-snooping biases. — [FINSABER, arXiv:2505.07078](https://arxiv.org/abs/2505.07078)
- Feature stores use point-in-time joins so that future values do not leak, and leakage is defined as using information not available at prediction time. — [Microsoft Learn](https://learn.microsoft.com/en-us/azure/machine-learning/offline-retrieval-point-in-time-join-concepts?view=azureml-api-2); [Feast docs](https://docs.feast.dev/v0.22-branch)
- Project practice already in place:
  - The frozen context and contracts are identified by SHA-256, and outcome status stays sealed after the proposal expires. — [COMPARISON_V1_V2.md](../../docs/evidence/hfl_scientific_consolidation_v75/COMPARISON_V1_V2.md)
  - DP-31 makes AI evaluation prospective only. DP-27 allows as-of queries only up to the decision date. DP-26 records Yahoo's limited intraday retention. — [DIRECAO_DO_PROJETO.md](../../docs/DIRECAO_DO_PROJETO.md)

### Inferences
- Prospective evaluation (DP-31) removes the model-memory look-ahead problem, because outcomes lie in the future. It does not remove input look-ahead or mislabeling. A delayed quote is legitimately available, but nothing from the current session is a "close" until after the 16:55–17:00 call. The snapshot must be labeled as partial and as-of its quote time.
- Proposed sealing checklist for an intraday snapshot:
  - instrument (internal id), value, currency;
  - source (Yahoo, provider ICE) and declared delay;
  - quote timestamp as reported, and fetch timestamp from the local clock with timezone, using the fetch time as the conservative "known-at" time since `regularMarketTime` is unvalidated;
  - session state (pre-open, continuous, closing call, closed) and fraction of session elapsed;
  - SHA-256 of the raw payload;
  - the version of the snapshot policy that selected it.

  Write the snapshot before the LLM call and include its hash in the sealed context hash. Because Yahoo deletes intraday bars (DP-26) and COTAHIST is daily, this record is the only evidence of the price the system used.
- Anonymization compatibility: if analysts ever receive intraday information, it should be relative (return since t-1 close, or distance from t-1 levels) and coarsely rounded, never an absolute price level. Absolute levels are an identification key that undercuts the no-ticker/no-date design. This follows from the distraction and memorization findings above, not from a direct test.
- Data clock and price clock should be stated explicitly in every run record, for example `data_asof = session t-1 (complete)` and `price_asof = 2026-10-19T14:20:05-03:00 (fetch), quote 14:05, ~15-min delayed`. Two runs are then comparable only if they share the data clock and have declared price clocks. This makes the "time machine" property auditable.

### Gaps
- No LLM-finance paper was found that studies intraday snapshots for agents with a daily decision horizon specifically. The guidance above is assembled from adjacent results (point-in-time models, anonymization, live benchmarks, feature-store as-of joins).
- Some quantitative claims in Profit Mirage come from secondary summaries and were not checked against the full text.
- No source was found on clock-synchronization or timestamp-semantics guidance for Yahoo `.SA` quotes. The project's own audit lists this as unvalidated.
